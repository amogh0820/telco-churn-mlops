# Telco churn prediction — training to production

A churn model for a telecom subscriber base: a trained scikit-learn pipeline
served behind FastAPI, tracked with MLflow, containerised with Docker, tested
end to end, and deployed publicly on Render's free tier.

**Live demo:** https://telecom-churn-predictor-5ptx.onrender.com/
**Repository:** https://github.com/amogh0820/telco-churn-mlops

> The first request after a period of inactivity takes 30-60 seconds to
> respond -- Render's free tier sleeps an idle service and wakes it on the
> next request. That's expected, not a bug; see "Deploying to Render" below.

---

## What this does

A telecom operator loses about a quarter of its subscriber base. The
retention team wants to know who is about to leave, early enough to
intervene. The model scores each subscriber and the API returns a probability
plus a recommendation, and a small web client lets anyone try it without
writing a request by hand.

The recommendation is the interesting part. Most churn projects report
accuracy at a 0.5 cut-off, which is arbitrary and usually wrong: a retention
call costs money whether or not the customer was leaving, and a saved
customer is worth far more than the call. This project picks the decision
threshold that maximises expected campaign value under stated cost
assumptions, and reports the gap against the naive 0.5 baseline.

Those assumptions live in `src/config.py`, are recorded in the trained
model's own metadata, and are surfaced by the `/model-info` endpoint -- the
frontend reads them from there rather than hardcoding a copy:

| Assumption | Value |
|---|---|
| Cost of one retention contact | $60 |
| Margin lost when a customer churns | $500 |
| Share of targeted churners actually saved | 35% |

**Data:** the IBM Telco customer-churn sample -- 7,043 customers, 21 columns,
pulled straight from the [IBM repository](https://github.com/IBM/telco-customer-churn-on-icp4d)
by `make data`. No Kaggle account needed, no manual download, and the
download step asserts the shape so a silent upstream change fails loudly.

## Architecture

```
  IBM Telco CSV (downloaded, shape-asserted)
        |
        v
  src/data/preprocess.py --> stratified train/test split
        |
        v
  src/models/train.py
    - 3 model families x randomised hyper-parameter search (5-fold CV)
    - every candidate logged to MLflow as a nested run
    - threshold chosen on out-of-fold predictions, never on test
    - winner -> MLflow registry (@champion) + artifacts/model.joblib
        |
        v
  src/api/main.py (FastAPI)
    GET  /            -> the scoring UI (demo/index.html), same origin as the API
    POST /predict, /predict/batch
    GET  /health, /model-info, /metrics
        |
        v
  one Docker image -> one Render web service -> one public URL
```

One Docker image, one Render service, one URL: `demo/index.html` is a plain
static file, but `main.py` serves it directly at `GET /` when the image
bundles it (the main `Dockerfile` does; see "Deploying" for the one build
that intentionally doesn't). That means the frontend and the API are always
same-origin -- no CORS configuration to get right, no second Render service
to create, and no separate URL to keep track of for a resume link.

### Four decisions worth defending in an interview

**Feature engineering lives inside the scikit-learn pipeline.** The API
receives only the 19 raw fields a billing system knows. Derived features
(`avg_monthly_spend`, `charge_drift`, `num_addons`, `tenure_bucket`) are
computed by a `FunctionTransformer` that is part of the fitted pipeline, so
the exact code that ran during training runs at serving time. Training/serving
skew is not prevented by discipline here; it is prevented by there being one
code path.

**The threshold is tuned on out-of-fold training predictions.** Tuning it on
the test set would leak. The test set is touched exactly once, at the end.

**Blank `TotalCharges` is reconstructed, not median-imputed.** All 11 blanks
belong to `tenure == 0` customers who have not been billed yet, so their true
lifetime spend is 0. Median imputation would invent ~$1,400 of history for
the newest customers in the base -- who are also the highest-risk group.
There is a regression test for this specific bug
(`test_blank_total_charges_becomes_nan_not_a_carried_over_value`).

**The trained model is committed to the repository.** Every other generated
file (raw data, MLflow runs, coverage reports) is gitignored, but
`artifacts/model.joblib` and `artifacts/model_metadata.json` are a deliberate
exception -- see "Deploying to Render" for why.

## The frontend

`demo/index.html` and `demo/app.js` are a small, dependency-free client: no
build step, no framework, one HTML file and one script. It's laid out as a
request/response tool rather than a dashboard, because that's what it
actually is -- a form on the left builds a `POST /predict` body field-for-field
from `src/api/schemas.py`'s `CustomerFeatures` model; a panel on the right
shows the literal HTTP response, then one plain-language reading of it.

A few things worth knowing if you're extending it:

- **Nothing about risk or the threshold is hardcoded.** The status panel's
  "threshold picked to maximise expected value of..." line and the numbers
  under it come from `GET /model-info`, which forwards whatever
  `src/models/train.py` recorded in the model's metadata. Retrain with
  different cost assumptions in `src/config.py` and this panel changes with
  it -- there is nothing in `app.js` to also go update.
- **The endpoint field defaults to the page's own origin** when served over
  http(s) (Render, `make serve`, Docker), so it works with no configuration
  the moment you open it. It only falls back to `http://localhost:8000` when
  there is no origin to default to (opening the file directly, `file://`).
- **The logic is split from the DOM on purpose.** Everything in `app.js`
  above the `if (typeof document !== "undefined")` line is pure -- it takes
  plain values and returns plain values -- so `app.test.js` can exercise it
  with Node and no browser. Run it with `make test-frontend`.
- **Every fixture in `app.test.js` is copied from the real contract**, not
  invented: the field list matches `CustomerFeatures`, the response shapes
  match `PredictionResponse` and the actual `/model-info` payload, and the
  422 body matches FastAPI's own validation-error format.

## MLflow

`src/models/train.py` opens one parent run per training sweep and one nested
run per model family (logistic regression, random forest, hist gradient
boosting), logging every candidate's hyperparameters and cross-validated
PR-AUC. The winner is registered under `REGISTERED_MODEL_NAME` and pointed at
by the `PRODUCTION_ALIAS` alias (`@champion`) -- `models:/telco-churn-classifier@champion`
always resolves to whatever version currently holds that alias, which is what
a serving process wants to load without knowing a specific version number.

Locally this all runs against a file-backed tracking store (`./mlruns`);
`make mlflow` starts a UI on it at <http://localhost:5000>. The deployed API
never talks to a tracking server at all -- it loads the joblib pipeline baked
into its own image, which is what keeps the deployed container simple and
self-contained. `src/api/model_service.py` also supports loading from a
tracking server via `MLFLOW_MODEL_URI` if you want that story instead; it's
not what Render runs by default.

## Docker

One multi-stage `Dockerfile` builds the runtime image everything in this
project eventually runs from: local `docker run`, `docker-compose`, Render,
and the optional AWS path all build from the same file. It copies in `src/`,
`demo/`, and the two committed model-artifact files, installs only
`requirements.txt` (not the dev/training dependencies), and runs as a
non-root user behind `gunicorn` with `uvicorn` workers.

```bash
make docker-build   # requires artifacts/model.joblib -- run `make train` first
make docker-run      # http://localhost:8000
make smoke           # hits every endpoint of the running container
```

## Testing

```bash
make test             # pytest (unit + API contract tests) + the frontend tests
make test-frontend     # just the frontend tests (Node, no Python needed)
make lint              # ruff check + format --check
```

`tests/test_contract.py` fails the build if `src/config.py`'s feature list
and the Pydantic API schema ever drift apart -- a safeguard against exactly
the kind of silent skew a config change plus a forgotten schema update would
otherwise cause. `demo/app.test.js` does the same job for the frontend: its
fixtures are the real request/response shapes, so a schema change that isn't
also reflected in the UI shows up as a failing test, not a bug report.

## Deploying

### Render (this project's actual deployment)

Render's free tier needs no credit card for a web service: connect a GitHub
repository, it builds your Dockerfile, and you get an HTTPS URL. The
trade-offs, so nothing here is a surprise: a free web service gets 512MB RAM
and a fraction of a CPU core, sleeps after 15 minutes with no traffic and
takes 30-60 seconds to wake on the next request, and the workspace has 750
free instance-hours a month shared across free services (ample for a
low-traffic portfolio demo, since a sleeping service doesn't burn hours).

**Why the trained model is committed to the repository, not gitignored like
everything else it produces:** Render builds a Docker-runtime service by
running `docker build` directly against your repository's Dockerfile -- there
is no separate "run this command to train first" hook the way the GitHub
Actions CI has. The Dockerfile's `COPY artifacts/model.joblib ...` line needs
that file to already exist in the git checkout Render builds from. So: run
`make train` locally and commit the two files it writes
(`artifacts/model.joblib`, `artifacts/model_metadata.json`) before you push.
`.gitignore` has a specific exception carved out for exactly these two files.

**Steps** (all in the Render dashboard, no local CLI needed):

1. Push this repository to your own GitHub account (see the beginner-friendly
   guide below if you haven't done this before).
2. At <https://dashboard.render.com>, click **New +** -> **Web Service**.
3. Connect your GitHub account and pick the repository.
4. Render should detect the Dockerfile and offer **Docker** as the runtime.
   If it offers to auto-detect a different runtime instead, change it to
   **Docker** explicitly.
5. Set:
   - **Name:** anything -- this becomes part of the URL
     (`https://<name>.onrender.com`).
   - **Instance type:** **Free**.
   - **Health check path:** `/health` (this endpoint always returns HTTP 200
     even if the model failed to load, so it never blocks a deploy the way a
     stricter check could).
6. Under **Environment variables**, add:
   - `PORT` = `8000`
   - `WORKERS` = `1` (two workers, the image's own default, can be tight on
     512MB once pandas and scikit-learn's footprint are counted; one fits
     safely)
7. Click **Create Web Service**. The first build takes a few minutes.
8. Once it shows **Live**, open the URL. That's your live demo -- put it at
   the top of this README and on your resume.

A `render.yaml` Blueprint is also included, so **New +** -> **Blueprint**
pointed at this repository can do steps 3-7 in one pass. Render's Blueprint
schema has changed before, so if it doesn't import cleanly, the manual steps
above are the supported fallback -- they don't depend on that file at all.

**Redeploying after a change:** commit and push to your repository's default
branch. Render's GitHub integration rebuilds and redeploys automatically
(`autoDeploy` in `render.yaml`; the dashboard has the same toggle if you
created the service by hand). If you retrained the model, remember to `git
add artifacts/model.joblib artifacts/model_metadata.json` in that commit --
Render has no way to know a new model exists otherwise.

### Alternative deployment paths (kept for demonstration, not this project's actual deployment)

This project began from a tutorial that deploys to AWS, and the AWS path is
kept in the repository because it demonstrates real infrastructure --
ECR, EC2, IAM, SSM, GitHub OIDC -- that Render's simplicity intentionally
hides. A Hugging Face Spaces path is also kept as a second free, no-card
option. **Neither is what this project's live demo actually runs on**, and
neither is required to read, run, or deploy the project.

- **AWS (EC2 + ECR + SSM):** `deploy/`, `deploy/iam/`, and the `deploy` job
  in `.github/workflows/ci-cd.yml`. Needs an AWS account with a payment
  method on file (even the free tier requires one) and is not free to run
  continuously. The CI job for it skips cleanly -- it doesn't fail the
  build -- if `AWS_ROLE_ARN` isn't configured, so leaving it in the workflow
  costs a Render-only setup nothing.
- **Hugging Face Spaces:** `deploy/huggingface/`, `make deploy-hf`. Free,
  no card, but a separate platform from Render with its own Dockerfile that
  doesn't bundle `demo/` (Spaces has its own way of presenting a Space, so
  this path serves the API only).

Both are described in more detail in `deploy/iam/` and `deploy/huggingface/README.md`
respectively, for anyone who wants to reproduce that part of the original
tutorial.

## GitHub readiness

- **No secrets in the repository.** Every credential-shaped string in this
  README, `.env.example`, and the `deploy/` scripts is a placeholder
  (`hf_xxxxxxxxxxxxxxxxxxxx`, `ACCOUNT_ID`, etc.), never a real value.
- **`.gitignore` blocks `.env` and every `.env.*` variant** (keeping
  `.env.example` itself, which has no real values in it), plus any file
  matching `*credentials*`, `*secret*`, `*token*`, `*.pem`, or `*.key`, on
  top of the usual `.venv`, `__pycache__`, and build caches.
  `artifacts/model.joblib` and `artifacts/model_metadata.json` are the one
  deliberate, documented exception (see "Deploying to Render" for why);
  everything else generated by training, MLflow, or coverage stays out.
- Rotate anything if you ever paste a real key into a commit by mistake --
  removing it from the latest commit doesn't remove it from git history.

## Known limitations

- **No temporal validation.** The dataset is a static snapshot with no
  timestamps, so the split is random. A real deployment would train on
  customers as of month *t* and validate on churn observed in *t+1*; a random
  split is optimistic by comparison.
- **`/metrics` counters are per-worker.** Gunicorn can run more than one
  process and each keeps its own counts, so a scraper sees one worker's
  view. Fine for a health signal, wrong for exact request totals.
  `prometheus-client` with a multiprocess collector is the fix if that
  matters.
- **No input-drift monitoring.** `/metrics` covers service health, not data
  health. Logging request payloads and comparing feature distributions
  over time is the next thing to build.
- **Cost assumptions are illustrative.** In a real setting you would get
  them from the retention team and re-derive the threshold whenever they
  change.
